# Project Plan — Product Management (ASP.NET Core MVC)

Oct 8, 2026 · @Hirusha Fernando

## 1. Understanding of the Requirement

The task is to build a small product management web application in ASP.NET Core MVC, backed by SQL Server through EF Core code-first. It has two pages: a Product List page for CRUD and a Report page for two category-level calculations.

Working features are only part of it. The brief is mainly testing how the code is structured: service and repository layers, stored procedures, generic caching, delegates, a Bootstrap and jQuery UI, and MSTest unit tests with mocks. A project plan comes first, and the project is then built according to that plan.

### 1.1 Functional scope

The application manages a single entity, Product, across two pages.

**Product.** Each product has a Product ID, Name, Category, Price and Stock. Category is a plain text value on the product itself; the brief says a category table is not needed.

**Product List page.** Shows all products and lets the user create, edit and delete them.

**Report page.** Shows the two calculations:

1. The average price of products in each category.
2. The category with the highest stock value.

Each numbered requirement in the brief, and what I understand it to mean in practice.

### 1.3 Constraints

The brief sets four rules that shape how the code is written.

- **No database operations in controllers or views.** Controllers talk only to services, and only repositories touch the `DbContext`.
- **No templated or lazy code.** Controllers, views and data access are written by hand, not generated by scaffolding or copied from online templates.
- **No external code I cannot explain.** Any library or borrowed snippet must be something I understand well.
- **Plan first, then build.** The plan document is written before development, and the project follows it. The whole assessment is expected to take 3–4 days.

| Point in the brief | My reading |
| --- | --- |

## 2. Solution Approach

I will build one ASP.NET Core MVC project with a strict one-way call chain: Controller → Service → Repository → EF Core → SQL Server. Controllers hold no logic, services hold the business rules and caching, and the repository is the only code that touches the database.

The two report calculations run as stored procedures that a migration creates. A second project holds the MSTest unit tests for the service layer.

### 2.1 Architecture

&#91;embedded content: application architecture · 5 layers, cache and tests\]

A request enters at a controller, which calls a service. The service reads through the cache and falls back to the repository on a miss. The tests replace the repository and the cache with mocks.

### 2.2 Solution structure

The solution has two projects. The repository and service layers stay inside the MVC project as folders, each behind an interface.

### 2.4 Database

The database is built entirely from code: one table, seed data and two stored procedures, all applied through migrations.

**Products table.** The mapping is written with the Fluent API in its own configuration class, so the entity stays a plain C# class.

| Column | Type | Rules |
| --- | --- | --- |
| ProductId | `int`, identity | Primary key |
| Name | `nvarchar(100)` | Required |
| Category | `nvarchar(50)` | Required, indexed because the report groups on it |
| Price | `decimal(18,2)` | Required, check constraint: not negative |
| Stock | `int` | Required, check constraint: not negative |

**Migrations.** Three migrations, applied in order:

1. `InitialCreate` creates the Products table with its constraints and index.
2. `AddReportStoredProcedures` creates both procedures with `migrationBuilder.Sql`, and drops them again in `Down`.
3. `SeedProducts` inserts a few sample products so both pages show data on first run.

**Stored procedures.** The repository executes them through EF Core raw SQL and maps each result to a record. No calculation is done in C#.

| Procedure | Returns | Logic |
| --- | --- | --- |
| `dbo.usp_GetAveragePriceByCategory` | One row per category: category, average price, product count | `AVG(Price)` grouped by Category |
| `dbo.usp_GetHighestStockValueCategory` | Category and total stock value | `SUM(Price * Stock)` grouped by Category, top row only. `WITH TIES` returns every category that shares the top value. |

The `usp_` prefix is deliberate. SQL Server reserves `sp_` for system procedures.

### 2.5 Repository, services, caching and delegates

The repository only reads and writes. The services decide what is valid, what is cached and when the cache is cleared.

**Repository.** `IProductRepository` exposes the five CRUD methods and the two report methods. All methods are asynchronous and accept a `CancellationToken`. Read queries use `AsNoTracking`, since the results are only displayed or cached.

**Services.**

- `ProductService` handles CRUD. It trims Name and Category, rejects negative Price or Stock, and maps between the entity and DTOs.
- `ReportService` returns the two calculations from the repository.
- Both return immutable DTO records, never EF entities, so a cached object cannot be changed by its callers.

**Caching.** `ICacheService` has two generic methods, usable for any result type. Each takes a cache key and a delegate that loads the data.

| Method | Lifetime | Used for |
| --- | --- | --- |
| `CachedLongAsync<T>` | No expiry; kept until removed | The full product list |
| `CachedAsync<T>` | Absolute expiry of 5 minutes | A single product by ID, and both report results |

Caching is called only from the services. Keys are constants in one `CacheKeys` class, so a read and its invalidation can never use different keys.

**Delegates.** Callbacks are used in two places:

1. **Cache-miss callback.** The service passes a `Func<Task<T>>` that calls the repository. The cache service invokes it only when the key is missing, then stores the result.
2. **After-change callback.** `ProductService` holds a custom multicast delegate, `ProductChangedHandler(int productId)`. It is invoked after every successful create, update or delete. Its handlers remove the product list, the single-product entry and the report entries, so the next read loads fresh data.

### 2.6 Pages and UI

Both pages are Razor views styled with Bootstrap 5 and a small custom stylesheet. jQuery makes the Product List page work without full page reloads.

**Product List page (`/Products`).**

- A Bootstrap table lists every product, with Add, Edit and Delete actions.
- Add and Edit open a Bootstrap modal. jQuery loads the form as a partial view and submits it with AJAX.
- On a validation error the server returns the form with its messages. On success it returns the refreshed table rows.
- Delete asks for confirmation in a modal, then posts with AJAX.
- jQuery Validation checks input in the browser. The same rules run again on the server, from data annotations on the form view model.
- Every POST carries an anti-forgery token.

**Report page (`/Reports`).**

- A table shows each category with its average price and product count.
- A highlighted card shows the category with the highest stock value and that value.
- An empty state is shown when there are no products.

**Controllers.** `ProductsController` depends only on `IProductService`, and `ReportsController` only on `IReportService`. Neither references the `DbContext` or the repository. A missing product returns 404, and unexpected errors are logged and sent to a shared error page.

### 2.7 Unit testing

The tests target `ProductService`, with `IProductRepository` and `ICacheService` replaced by Moq mocks, so no test touches a database.

The cache mock simply invokes the load delegate it is given. That lets each test check the service's own logic and verify which cache entries it clears.

| Operation | Cases covered |
| --- | --- |
| Read all | Returns the products from the repository as DTOs; goes through `CachedLongAsync`. |
| Read by ID | Returns the product when found; returns nothing when the ID does not exist. |
| Create | Saves a valid product with trimmed values and clears the cache; rejects invalid input without calling the repository. |
| Update | Updates an existing product and clears the cache; reports not found for a missing ID and saves nothing. |
| Delete | Deletes an existing product and clears the cache; reports not found for a missing ID. |

Tests follow Arrange, Act, Assert and are named `Method_Scenario_ExpectedResult`. A few extra tests cover `MemoryCacheService`, confirming the load delegate runs once across repeated calls.

## 3. Issues That May Arise

Most of the risk in this project sits in three places: keeping cached data correct after writes, stored procedures that EF Core neither tracks nor type-checks, and forms loaded by AJAX that lose validation or anti-forgery protection.

Every issue below has a planned response. A few are accepted as known limitations instead of being solved, and are marked as such.

| Issue | Why it matters | How I will handle it |
| --- | --- | --- |
| "Highest stock value" can mean most units or highest monetary value | The two readings can name different categories | I use the total of Price × Stock, as stated in section 1. The logic lives in one stored procedure, so changing the reading takes one new migration. |
| Category is free text | Extra spaces or a typo split one category into several | The service trims the value before saving. SQL Server's default collation ignores case, so "Toys" and "toys" group together. Typos are not corrected. Accepted limitation, since the brief rules out a category table. In the UI use autocomplete dropdown to display existing categories which are fetched from the products table. |
| EF Core does not track stored procedures | They are not in the model snapshot, so migrations never generate or update them | Hand-written SQL in a dedicated migration, with a `Down` method that drops them. Any later change goes into a new migration. |
| Procedure results are mapped by column name at runtime | A renamed column or property still compiles, then fails when the report loads | Result records mirror the procedure's column names exactly. I run both procedures against the seed data before building the UI. |
| Cached data goes stale after a write | The product list has no expiry, so a new product would never appear | Every successful create, update or delete invokes the after-change callback, which removes the affected entries. |
| A caller modifies a cached object | Every later request sees the changed data | Services cache immutable records in read-only lists, never EF entities. |
| A multicast delegate with async handlers returns only the last handler's task | Earlier handlers would run unawaited, and their errors would be lost | `ProductChangedHandler` returns `void`. Its handlers only remove cache entries, which is a synchronous operation. |
| Forms loaded by AJAX are not picked up by jQuery Validation | Client-side validation silently stops working in the modal | The script re-parses the form with the unobtrusive validator each time a form is loaded. |
| Save is clicked twice, or a request fails | Duplicate products, or a user left without feedback | The button is disabled while a request is in flight. Failures show an error message in the modal. |
| The repository is mocked, and stored procedures cannot run on EF Core's in-memory provider | Unit tests can pass while a procedure returns wrong numbers | The procedures are verified by hand against seed data chosen so the expected results are easy to calculate. |

## 4. Pseudo Code

The pseudo code covers the logic the brief requires: generic caching with a load delegate, the product CRUD operations with their after-change callback, and the two calculations. It follows the design in section 2 and the responses in section 3.

### 4.1 Cache service

Both public methods share one helper and differ only in expiry. The `loadData` parameter is a delegate, called back only on a cache miss.

```
FUNCTION CachedLong<T>(key, loadData)
    RETURN GetOrLoad(key, loadData, expiry = NONE)

FUNCTION Cached<T>(key, loadData)
    RETURN GetOrLoad(key, loadData, expiry = 5 MINUTES)

FUNCTION GetOrLoad<T>(key, loadData, expiry)
    IF cache CONTAINS key THEN
        RETURN cache[key]

    value = AWAIT loadData()                // callback: runs only on a miss

    IF value IS NOT NULL THEN               // "not found" is never cached
        STORE value IN cache UNDER key
            WITH absolute expiry = expiry   // NONE means kept until removed
    RETURN value

FUNCTION Remove(key)
    DELETE key FROM cache
```

### 4.2 Product CRUD operations

Each operation is shown as one flow, from the user's action on the Product List page to the updated screen.

```
OPERATION View products                         // open the Product List page
    IF product list IS IN cache THEN            // kept until removed
        products = cached list
    ELSE
        products = ALL products FROM database
        STORE products IN cache
    SHOW products IN table

OPERATION Add product
    User clicks "Add"
    SHOW empty form IN modal
        WITH GetCategories() AS autocomplete suggestions FOR Category
    User enters Name, Category, Price, Stock AND clicks Save
    DISABLE Save button

    TRIM Name AND Category
    IF Name OR Category IS EMPTY OR too long, OR Price < 0, OR Stock < 0 THEN
        SHOW validation messages IN form
        ENABLE Save button
        STOP

    INSERT product INTO database
    INVOKE after-change callback
    REFRESH table, CLOSE modal, SHOW success message

OPERATION Edit product
    User clicks "Edit" ON a row
    IF product IS IN cache THEN                 // kept up to 5 minutes
        product = cached product
    ELSE
        product = product FROM database BY ID
        STORE product IN cache
    IF product DOES NOT EXIST THEN
        SHOW "product not found", REFRESH table
        STOP

    SHOW form IN modal FILLED WITH product values
        WITH GetCategories() AS autocomplete suggestions FOR Category
    User changes values AND clicks Save
    VALIDATE input AS IN Add product

    UPDATE product IN database
    INVOKE after-change callback
    REFRESH table, CLOSE modal, SHOW success message

OPERATION Delete product
    User clicks "Delete" ON a row
    SHOW confirmation WITH product name
    IF user cancels THEN STOP

    IF product DOES NOT EXIST IN database THEN
        SHOW "product not found", REFRESH table
        STOP

    DELETE product FROM database
    INVOKE after-change callback
    REFRESH table, CLOSE confirmation, SHOW success message

FUNCTION GetCategories()                        // feeds the Category autocomplete
    IF categories ARE IN cache THEN             // kept until removed
        RETURN cached categories
    categories = DISTINCT Category values FROM Products table, sorted A to Z
    STORE categories IN cache
    RETURN categories

CALLBACK after-change(productId)                // delegate, invoked after every successful write
    REMOVE product list FROM cache
    REMOVE categories FROM cache
    REMOVE product productId FROM cache
    REMOVE both report results FROM cache
```

### 4.3 Report calculations

Each calculation is shown as one flow. The grouping and the math run inside a stored procedure, and the result is cached for up to 5 minutes.

```
FUNCTION GetAveragePriceByCategory()
    IF result IS IN cache THEN RETURN it        // kept up to 5 minutes

    GROUP all products BY Category
    FOR EACH group
        AveragePrice = AVERAGE OF Price, rounded to 2 decimals
        ProductCount = NUMBER OF products
    result = groups SORTED BY Category

    STORE result IN cache
    RETURN result

FUNCTION GetHighestStockValueCategory()
    IF result IS IN cache THEN RETURN it        // kept up to 5 minutes

    GROUP all products BY Category
    FOR EACH group
        TotalStockValue = SUM OF (Price × Stock)
    result = the group WITH the highest TotalStockValue

    STORE result IN cache
    RETURN result
```
